# 00 —— 整体控制框架

> 这份文档不推导任何公式，只回答一个问题：**11 个里程碑拼在一起，到底是一台什么样的机器？**
> 每个模块的推导见各自的文档（01–11），这里只讲它们之间的**接口、频率和数据流**。

---

## 1. 一张图看全貌

整个仓库是**一套共享的底层 + 两条控制路线**：

```
                         ┌─ 底层：机器人模型 ─────────────────────────────┐
                         │  M1 运动学   FK / IK / 雅可比 J(q)               │
                         │  M2 动力学   M(q)a + h = Sᵀτ + Σ Jᵢᵀfᵢ，SRBD     │
                         └──────────────┬──────────────────────────────────┘
                                        │ 两条路线都建立在它上面
              ┌─────────────────────────┴─────────────────────────┐
              ▼                                                   ▼
  路线 A：基于模型的分层控制（M3–M8，M11 闭环）        路线 B：强化学习（M9、M10）
  ───────────────────────────────────────             ──────────────────────────
  速度指令                                             速度指令 + 传感器观测
    → 步态调度 M4 （哪几条腿着地）                       → 神经网络策略 π(obs)
    → 落脚点 M6   （下一步踩哪）                         → 12 个关节目标角
    → 摆动轨迹 M5 （腿在空中怎么走）                     → 电机内部 PD → 力矩
    → 凸 MPC  M7  （着地脚推多大力）  50 Hz
    → WBC     M8  （12 个关节力矩）   1 kHz             M10 残差 RL：
    → 电机                                              目标角 = 名义步态(M1/4/5/6)
                                                                 + α · 策略修正
  被控对象：MuJoCo（M11）                               被控对象：Isaac Lab（GPU 4096 份并行）
```

**M3 状态估计**是两条路线在真机上都需要的"眼睛"。目前它是单独验证的，**还没有接进 M11 闭环**——仿真里控制器直接读真值状态（见第 7 节）。

## 2. 路线 A 的分层结构：为什么要分层

一个控制器同时要处理"未来 0.3 秒怎么保持平衡"和"这 1 毫秒电机出多少力"，两件事的时间尺度差了 300 倍，模型精度要求也完全不同。所以拆成四层，**越往上看得越远、模型越粗、跑得越慢**：

| 层 | 模块 | 频率 | 用的模型 | 回答的问题 | 输出 |
|---|---|---|---|---|---|
| 规划层 | M4 步态 + M6 落脚点 + M5 摆动轨迹 | 每周期查表/闭式计算 | 倒立摆 LIPM、几何 | 哪条腿什么时候抬、踩哪、怎么走 | 接触序列、落脚点、足端参考轨迹 |
| 预测层 | M7 凸 MPC | **50 Hz**（接触切换时立即重解） | 单刚体 SRBD（13 维状态） | 未来 10 步 × 30 ms = 0.3 s 内，怎样分配地面力最好 | 每只支撑脚的地面反力 f（世界系，4×3） |
| 执行层 | M8 WBC | **1 kHz** | 完整 18 自由度刚体动力学 | 在物理上真正可行的前提下，怎样最接近所有任务 | 12 个关节力矩 τ |
| 被控对象 | MuJoCo（M11） | 1 kHz（与 WBC 同频） | 独立物理引擎 | —— | 新的状态 (q, v) |

> **无人机类比。** 多旋翼的级联控制是"位置环 → 姿态环 → 角速度环 → 混控"，越内环越快。
> 这里的 MPC ≈ 位置/姿态环（决定"要多大的合力和合力矩"），WBC ≈ 混控（把合力分配到执行器）。
> **类比断掉的地方**：混控矩阵是常数，而腿的"混控"J(q) 随姿态变；无人机的推力只能沿机体 z 轴，
> 而脚的力可以有三个方向，但受摩擦锥限制、只能推不能拉、只在着地时存在。
> 这三点就是 WBC 必须解一个带约束 QP、而不是乘一个矩阵的原因。

## 3. 一个 1 ms 控制周期里发生了什么

对应代码：[`LocomotionController.step`](../locomotion/controller.py)（第 169 行起），外层循环在 [`sim/episode.py`](../sim/episode.py)。

```
输入：t, q(19), v(18), 速度指令 [vx, vy], 偏航角速度指令
│
├─ ① 参考生成                                              controller.py:192
│     把速度指令积分成"躯干应该在哪"的参考位置 body_xy_ref 和 yaw_ref。
│     参考离实测超过 10 cm 就截断，防止被推一下后 PD 要求不合理的回拉。
│
├─ ② 步态调度 M4         GaitScheduler.contact(t)           controller.py:199
│     trot：周期 0.4 s，占空比 0.5，对角腿 FL+RR / FR+RL 交替。
│     输出：4 条腿是否支撑（bool×4）。刚离地的腿记下离地点。
│
├─ ③ 落脚点规划 M6       FootstepPlanner.plan(...)          controller.py:206
│     Raibert：落脚点 = 落地时刻的髋投影 + 速度误差反馈。
│     输出：每条摆动腿的落地点（世界系 xyz）。
│
├─ ④ 凸 MPC M7（条件触发）                                  controller.py:213
│     触发条件：距上次 ≥ 20 ms，或者接触集合刚变（有脚落地/抬起）。
│     输入：13 维状态 [rpy, 质心位置, 角速度, 质心速度, g]、
│           未来 10 步的参考轨迹、接触序列、落脚点。
│     解一个条件化后的稠密 QP（摩擦金字塔约束）。
│     输出：未来 10 步每只脚的力计划 (10, 4, 3)，按时间取当前这一步。
│
├─ ⑤ 组装 WBC 任务                                          controller.py:221
│     · 躯干位置任务：PD(参考位置 − 实际) → 期望线加速度
│     · 躯干姿态任务：PD(参考姿态 − 实际) → 期望角加速度
│     · 每条摆动腿：BezierSwing(离地点 → 落脚点) 给 p/v/a 参考，
│                    前馈加速度 + 笛卡尔 PD → 期望足端加速度   (M5)
│     · 支撑腿的期望力 = MPC 的力计划
│
├─ ⑥ WBC 求解 M8         WholeBodyController.solve(...)     controller.py:241
│     决策变量：广义加速度 a(18) + 接触力 f(3×支撑脚数)
│     硬约束：躯干 6 行动力学（躯干上没有电机）、支撑脚不动、
│             摩擦金字塔、关节力矩上限
│     软目标：各任务加权误差 + 跟踪 MPC 的力（权重高，但可以让步）
│     τ 不是决策变量，由动力学后 12 行算出来。
│
└─ 输出：12 个关节力矩 τ  →  sim.step(τ)  →  下一周期      episode.py:135
```

**两个设计细节，面试常问：**

1. **MPC 为什么在接触切换时立即重解？** 两次 MPC 之间用的是旧的力计划。如果不重解，一只刚落地的脚可能最多 20 ms 拿不到力，而刚抬起的脚反而还被要求出力。
2. **MPC 的力为什么是软约束，而不是硬约束？** MPC 用的单刚体模型忽略了腿的质量（M2 量化过：腿快速摆动时，躯干角加速度误差中位数达 43%）。如果硬性复现这些近似的力，摆动腿任务会被牺牲，QP 甚至会无解。分工是：**MPC 负责大方向对，WBC 负责物理上真的做得到；两个模型冲突时，让完整模型赢。**

## 4. 模块之间的数据接口

想读懂代码，先看清每个模块"吃什么、吐什么"。约定：**全部使用世界系**，只有一处例外——Pinocchio 浮动基座的 `v[0:6]`、`a[0:6]` 是**机体系**的（`_body_task` 的文档说明了如何转换）。

| 模块 | 类 / 函数 | 输入 | 输出 |
|---|---|---|---|
| M1 运动学 | `kinematics/` | 关节角 q | 足端位置、雅可比 J(q) |
| M2 动力学 | `RigidBodyDynamics` | q, v | M(q)、h(q,v)、质心、SRBD 参数 |
| M3 状态估计 | `state_estimator/eskf.py` 等 | IMU、关节编码器、力矩 | 躯干位姿/速度估计、足端力、接触概率 |
| M4 步态 | `GaitScheduler` | 时间 t | 当前接触 bool×4、摆动进度、未来 N 步接触序列 |
| M6 落脚点 | `FootstepPlanner.plan` | t、躯干位置/速度、速度指令、偏航 | 每条摆动腿的落地点 |
| M5 摆动轨迹 | `BezierSwing` | 离地点、落地点、抬腿高度 | 任意相位的足端 p / v / a |
| M7 MPC | `ConvexMPC.solve` | 13 维状态、参考轨迹、接触序列、落脚点 | 力计划 (N, 4, 3) |
| M8 WBC | `WholeBodyController.solve` | q, v、支撑腿集合、期望力、任务列表 | 关节力矩 τ(12)、实际接触力 |
| 串联 | `LocomotionController.step` | t, q, v、速度指令 | `ControlOutput`（τ 及诊断量） |
| 仿真 | `MujocoGo2.step` | τ | 新的 q, v、真值接触力 |

**变量尺寸速记**：`q` 19 维（躯干位置 3 + 四元数 4 + 关节 12），`v` 18 维（躯干线速度 3 + 角速度 3 + 关节 12）。四元数比 3 维转动多一个分量，所以 q 比 v 多一维。

## 5. 三个模型，三种精度

路线 A 内部同时存在三个"世界观"。理解它们的差异，就理解了为什么要分层：

| 模型 | 谁在用 | 状态维度 | 忽略了什么 | 换来什么 |
|---|---|---|---|---|
| 倒立摆 LIPM | M6 落脚点 | 质心水平 2 维 | 姿态、腿质量、高度变化 | 闭式解，微秒级 |
| 单刚体 SRBD | M7 MPC | 13 | 腿的质量与惯量 | 动力学近似线性 → 凸 QP → 能预测 0.3 s |
| 完整刚体动力学 | M8 WBC | 18 自由度 | 几乎没有（电机模型、柔性除外） | 物理上精确，但只能看当下这一瞬 |
| MuJoCo | 被控对象 | —— | —— | 独立实现，用来检验上面三个模型 |

## 6. 路线 B：强化学习框架

```
Isaac Lab：4096 只 Go2 在 GPU 上并行
│
├─ 观测 obs（Actor 看）：角速度、重力方向、速度指令、关节角/速度、上一次动作
│     （Critic 额外看躯干线速度 —— 非对称 Actor-Critic；残差版再加名义动作、步态相位 sin/cos）
│
├─ 策略网络 π（Actor）50 Hz → 动作 a（12 维）
│
├─ 动作 → 关节目标角
│     纯 RL  ：q_des = q_default  + 0.25 · a
│     残差 RL：q_des = q_nominal(t) + α · a     （α 课程式从 0.05 增大到 0.25）
│
├─ 电机内部 PD：τ = Kp(q_des − q) − Kd·q̇      物理 200 Hz
│
├─ 奖励 r：速度跟踪、姿态、力矩与加速度、动作变化率、
│          步态相位(M4)、捕获点(M6)、抬脚高度(M5)、防打滑(M7 摩擦)
│
└─ PPO 更新（Actor 出动作、Critic 打分、GAE 估计优势）→ 下一轮采样
```

- 物理步长 5 ms（200 Hz），策略每 4 个物理步出一次动作（`decimation=4`，即 50 Hz）。见 [`isaac/go2_env_cfg.py`](../isaac/go2_env_cfg.py)。
- **名义控制器** `q_nominal(t)` 来自 [`rl/nominal_controller.py`](../rl/nominal_controller.py)：把 M4 相位、M6 Raibert、M5 抬腿曲线、M1 闭式 IK 用批量 torch 重写一遍，一次算 4096 份。
- **为什么 MPC + WBC 不能当名义控制器？** 它们每一步都要解 QP，而 QP 求解器是串行的、跑在 CPU 上、迭代次数随数据变化，没法批量化成 GPU 上的 4096 份。能进 GPU 的恰好是闭式的那一半。

**路线 A 和路线 B 的根本区别在最后一环：**

| | 路线 A（MPC + WBC） | 路线 B（RL） |
|---|---|---|
| 网络/控制器输出 | 关节**力矩** | 关节**目标角** |
| 力从哪来 | QP 显式算出接触力 | 由 PD 的"弹簧"间接产生 |
| 平衡靠什么 | 模型 + 优化 | 训练数据里学到的经验 |
| 加约束（摩擦、限幅） | 直接写进 QP，必然满足 | 只能写进奖励，"尽量"满足 |
| 换任务的成本 | 改代价函数 / 任务权重 | 改奖励后重新训练 |
| 单步计算量 | 解两个 QP，毫秒级 | 一次网络前向，微秒级 |

> M10 的一个关键发现：纯位置控制的解析步态在 Go2 默认的软 PD 增益下**几乎没有速度控制能力**——
> 指令 0.5 m/s，实际不到 0.06 m/s。这就是路线 A 必须走力矩控制的原因；
> 而残差 RL 让策略去学会"补上"这部分缺口。

## 7. 这套框架现在走到了哪一步

```
            已完成并闭环验证                    已完成，但未接入闭环          未做
  ┌──────────────────────────────────┐   ┌──────────────────────────┐   ┌──────────────┐
  │ M4→M6→M5→M7→M8 → MuJoCo（M11）     │   │ M3 ESKF 状态估计           │   │ 真机部署      │
  │ 平地 trot 0.25–1.5 m/s，抗侧推     │   │ 接触检测 → 反馈给 WBC      │   │ 崎岖地形闭环  │
  │ M9 纯 RL、M10 残差 RL（平地）       │   │ MPC 异步线程（现在同步，    │   │ C++ 实时移植  │
  │ M11 足端力观测器（离线评估）       │   │   p99 7.7 ms > 1 ms 周期） │   │ 残差 RL 地形  │
  └──────────────────────────────────┘   └──────────────────────────┘   └──────────────┘
```

如果上真机，路线 A 的数据流会有三处变化：

1. `step()` 的输入 `(q, v)` 不再是仿真真值，而是 **M3 ESKF** 融合 IMU 与腿部里程计后的估计值。
2. 步态调度给出的"计划接触"要和 **足端力观测器** 检测到的"实际接触"对比：脚提前触地就提前切换成支撑，迟迟没落地就继续往下探。
3. MPC 要放进独立线程异步求解，WBC 线程只读取最近一次的力计划，才能保证 1 kHz 不掉帧。

## 8. 建议的阅读顺序

1. 先读 [`locomotion/controller.py`](../locomotion/controller.py) 的模块文档和 `step()`，对照本文第 3 节，搞清楚一个周期的流程。

4. 最后读两个 QP：[`mpc/srbd_mpc.py`](../mpc/srbd_mpc.py) 和 [`whole_body_controller/wbc.py`](../whole_body_controller/wbc.py)，配合文档 07、08 的推导。
5. 跑一下，看结果和图：

```bash
conda activate env_isaaclab_recovered
python scripts/eval_mujoco.py && python scripts/viz_mujoco.py
```
